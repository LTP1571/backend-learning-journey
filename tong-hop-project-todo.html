1. Bức tranh tổng thể

Sinh ra để giải quyết chuyện gì: hai máy tính ở hai nơi cần trao đổi dữ liệu, nhưng chỉ gửi cho nhau được văn bản. Toàn bộ Spring Boot tồn tại để biến văn bản đó thành object Java, cho code xử lý, rồi biến ngược object thành văn bản gửi trả.

Một request đi qua đúng chuỗi này:

Postman gửi văn bản JSON qua HTTP
↓
Spring đọc URL + method, tìm đúng method Controller
↓
Jackson đọc JSON → dựng object TodoRequest
↓
Validation kiểm @NotBlank — sai thì dừng ngay tại đây, trả 400
↓
Controller gọi Service, không tự quyết gì
↓
Service quyết định làm gì, dựng Todo, gọi Repository
↓
Repository → Hibernate điền SQL → PostgreSQL
↓
database trả dòng dữ liệu → Hibernate dựng lại object Todo
↓
Service đổi Todo → TodoResponse (method toResponse)
↓
Jackson đổi TodoResponse → văn bản JSON
↓
Postman nhận status + body

Hai chỗ đổi dạng dữ liệu là chỗ hay nhầm nhất: văn bản → object ở đầu vào, và object → văn bản ở đầu ra. Object chỉ tồn tại trong bộ nhớ máy chủ; thứ đi qua dây mạng luôn là văn bản.

2. Bốn tầng kiến trúc

Sinh ra để giải quyết chuyện gì: nếu nhét hết vào một class, sửa một chỗ vỡ mọi chỗ, và không test được từng phần riêng. Chia tầng để mỗi tầng có đúng một loại việc.
TầngClassViệc duy nhất của nó
EntityTodoMô tả một dòng trong bảng database
RepositoryTodoRepositoryNói chuyện với database
ServiceTodoServiceQuyết định làm gì
ControllerTodoControllerNhận request, trả kết quả

Quy tắc đã tự chốt

  • Controller nhận request và trả kết quả — không quyết định gì.
  • Service quyết định làm gì — mọi if/else nghiệp vụ nằm ở đây.
  • Repository nói chuyện với database — không biết gì về HTTP.
  • Method Controller dài hơn một dòng là gần như đang lấn việc của Service.
  • Service không được nhắc mã HTTP trong message exception. Service không biết HTTP tồn tại; việc dịch exception thành 404 là của handler.
Bẫy đã dính: gọi thẳng repository trong Controller. Chạy được, nhưng phá vỡ tầng — Controller lúc đó vừa nhận request vừa nói chuyện với database, và mọi logic nghiệp vụ mất chỗ để ở.

Phụ thuộc chỉ đi một chiều

Controller biết Service, Service biết Repository, Repository biết database. Không có chiều ngược. Repository không được biết Service tồn tại. Nhờ vậy đổi Controller không ảnh hưởng Repository.

3. Entity & JPA

Sinh ra để giải quyết chuyện gì: database nghĩ theo bảng và dòng, Java nghĩ theo class và object. ORM (Object-Relational Mapping) là lớp dịch giữa hai cách nghĩ đó — Hibernate là bản cài đặt cụ thể của ý tưởng ORM.
@Entity
public class Todo {
    @Id
    @GeneratedValue
    private Long id;
    private String title;
    private boolean completed;
    // getter + setter cho cả ba field
}
Thành phầnNó nói với Hibernate điều gì
@EntityClass này ứng với một bảng. Không có nó, Hibernate coi như class thường và bỏ qua.
@IdField này là khóa chính — thứ phân biệt dòng này với dòng khác.
@GeneratedValueĐừng chờ code gán id, database tự sinh.
Field thườngMỗi field không đánh dấu gì thành một cột cùng tên.
Getter/setterHibernate và Jackson đều đọc/ghi field qua getter và setter, không đọc field trực tiếp.
Phân tầng thuật ngữ
Thuộc: @Entity, @Id, @GeneratedValue
Hiểu ý: ORM, Hibernate là bản cài đặt của JPA
Quên được: tên đầy đủ các interface trong đặc tả JPA
Vì sao boolean completed có getter là isCompleted() chứ không phải getCompleted(): quy ước Java — kiểu boolean dùng tiền tố is. Jackson và Hibernate đều theo quy ước này. Gõ sai tên getter thì field biến mất khỏi JSON mà không báo lỗi gì.

4. Sinh id & sequence (id nhảy lên 52)

Sinh ra để giải quyết chuyện gì: mỗi lần xin một id là một lượt đi-về với database. Insert 1000 dòng thành 2000 lượt. Để tránh, Hibernate xin sẵn một dải id rồi tự phát dần trong bộ nhớ.

Cơ chế

  1. @GeneratedValue không ghi strategy → Hibernate chọn SEQUENCE.
  2. Tạo sequence trong database với bước nhảy allocationSize = 50 (mặc định).
  3. Một lần nextval trả về một số → Hibernate hiểu là "50 id kế tiếp thuộc về tôi".
  4. Cấp dần cho từng object mới, không hỏi lại database.

Vì sao id nhảy cóc

Dải id chỉ sống trong bộ nhớ của app. Tắt app là phần chưa dùng mất luôn — database không biết bạn xài tới đâu, nó chỉ nhớ đã phát dải nào. Khởi động lại, Hibernate xin dải mới, số bắt đầu từ chỗ dải cũ kết thúc. Restart vài lần là id nhảy quãng lớn.

Chốt: không sửa. Id chỉ cần duy nhất, không cần liên tục. Khoảng trống trong id là bình thường ở mọi hệ thống thật — xoá dòng cũng để lại lỗ hổng tương tự. Muốn id liền mạch phải đổi sang IDENTITY, đánh đổi là mất khả năng batch insert.
Phân tầng thuật ngữ
Thuộc: sequence, allocationSize
Hiểu ý: strategy AUTO / SEQUENCE / IDENTITY
Quên được: tên sequence mặc định, cách khai @SequenceGenerator

5. Hibernate sinh SQL

Ai sinh SQL, và sinh lúc nào

Hibernate soạn khung SQL lúc app khởi động, không phải mỗi lần gọi save(). Khung đó có sẵn dấu ? ở chỗ giá trị. Lúc save() chạy, Hibernate chỉ điền giá trị vào dấu ? rồi gửi đi.

save() chọn INSERT hay UPDATE thế nào

Trạng thái id của objectHibernate làm gì
id == nullINSERT — đây là object mới
id != nullUPDATE — object này đã có trong database

UPDATE không kiểm tra tồn tại trước. Nó chạy câu lệnh rồi xem số dòng bị ảnh hưởng — 0 dòng nghĩa là không có gì để sửa. Đây là lý do trong update() phải tự findById trước để ném 404, chứ không thể dựa vào save() báo lỗi.

ddl-auto

Thuộc tính spring.jpa.hibernate.ddl-auto quyết định Hibernate có tự tạo/sửa bảng theo Entity hay không. Đây là lý do đến giờ chưa từng viết một câu SQL nào bằng tay — và cũng là lý do lịch có 2 ngày SQL thuần trước khi vào DBI202.

Đã đồng ý không đào sâu: vì sao Hibernate chọn soạn khung lúc khởi động thay vì soạn mỗi lần save. Biết là nó làm vậy, đủ dùng.

6. Repository

Sinh ra để giải quyết chuyện gì: mọi bảng đều cần đúng nhóm thao tác giống nhau — thêm, tìm, sửa, xoá. Viết tay cho từng bảng là lặp vô nghĩa. JpaRepository cho sẵn cả bộ.
public interface TodoRepository extends JpaRepository<Todo, Long> {
}

Thân rỗng, nhưng dùng được ngay hàng chục method. Hai tham số trong ngoặc nhọn: Entity nào và kiểu của khóa chính.

Đây là interface, không phải class — không có dòng lệnh nào bên trong. Spring tự sinh bản cài đặt lúc chạy. Đó cũng là lý do không viết new TodoRepository() bao giờ.

Các method đã dùng

MethodTrả vềGhi chú
save(entity)Entity đã lưuVừa INSERT vừa UPDATE, tuỳ id. Phải nhận Entity, không nhận DTO.
findById(id)Optional<Todo>Không tìm thấy thì Optional rỗng, không phải null
findAll()List<Todo>Không có thì trả list rỗng, không phải null
deleteById(id)voidKhông báo gì nếu id không tồn tại

Bẫy đã dính 3 lần: đưa TodoRequest (DTO) thẳng cho repository.save(). Repository chỉ biết Entity — DTO không phải @Entity, Hibernate không biết lưu nó vào bảng nào. Phải dựng Todo mới, set field từ DTO, rồi mới save.
Bẫy tên method: lẫn tên của Repository sang Service. Repository dùng save, deleteById; Service dùng create, update, delete. Hai tầng, hai bộ tên — cố ý khác nhau để nhìn tên là biết đang ở tầng nào.

7. Optional

Sinh ra để giải quyết chuyện gì: trả null khi không tìm thấy là nguồn lỗi kinh điển của Java — người gọi quên kiểm tra, chương trình vỡ ở chỗ khác hẳn. Optional là cái hộp buộc người gọi phải mở ra, và mở thì phải nói rõ "nếu rỗng thì làm gì".

findById trả Optional<Todo> — không phải Todo. Muốn lấy object bên trong phải xử lý trường hợp rỗng.

orElseThrow

Là method của Optional, không phải của Repository. Nghĩa: có thì đưa ra, rỗng thì ném exception mình chỉ định.

Vì sao không cần import java.util.Optional: chữ "Optional" không hề xuất hiện trong file Service. Nó chỉ là kiểu trả về trung gian, bị orElseThrow tiêu thụ ngay trên cùng một dòng. Java chỉ bắt import những tên viết ra trong file.

8. Service & bean

@Service
public class TodoService {
    private final TodoRepository repository;

    public TodoService(TodoRepository repository) {
        this.repository = repository;
    }
    // findAll, findById, create, update, delete
    // + private TodoResponse toResponse(Todo todo)
}

bean

Chỉnh cuối sau 3 lần hiểu sai: bean là object — không phải bản thiết kế, không phải khái niệm trừu tượng. Điểm khác duy nhất so với object thường: nó do Spring tạo và giữ, thay vì mình gõ new.

Bean vẫn đổi được trạng thái bên trong. Thứ không đổi là: Spring không tạo cái thứ hai. Cả app dùng chung một object đó.

Constructor injection

Service cần Repository. Thay vì tự new, nó khai trong constructor — Spring thấy vậy thì tự đưa bean Repository vào lúc dựng Service.

  • @Service đánh dấu để Spring biết cần tạo bean từ class này.
  • final đảm bảo sau khi gán trong constructor thì không ai đổi được nữa.
  • Nhờ nhận từ ngoài, sau này test có thể đưa vào một Repository giả.

Gom việc dựng TodoResponse vốn lặp ở 4 chỗ về một chỗ. Thêm field mới vào TodoResponse thì chỉ sửa một nơi, không sợ sót.

Vì sao để private: không phải để giấu dữ liệu — mà để bề mặt công khai của Service nhỏ lại. Đây là việc nội bộ; nếu để public, Controller gọi được, và ngày mai đổi tên hay đổi tham số thì phải sửa cả chỗ ngoài Service.
Vì sao dùng được cả trong vòng lặp lẫn gọi lẻ: nó không giữ trạng thái gì. Không đọc field của class, không sửa gì bên ngoài, không nhớ lần gọi trước. Mọi thứ cần nằm trọn trong tham số; mọi thứ tạo ra đi hết vào giá trị trả về. Gọi lần 1 và lần 500 hoàn toàn độc lập.
Bốn mức truy cập — thuộc lòng

protected → cùng package + class con

10. ResponseEntity

Sinh ra để giải quyết chuyện gì: trả thẳng object thì Spring tự gắn status 200 cho mọi trường hợp. Muốn tự chọn status (201, 204, 404) thì cần một cái vỏ chứa được cả ba phần của response.

Ba ngăn của một HTTP response:

NgănChứa gì
StatusCon số: 200, 201, 204, 400, 404...
HeaderThông tin phụ về response (kiểu nội dung, độ dài...)
BodyNội dung thật — JSON hoặc chuỗi, có thể rỗng

Kiểu trong ngoặc nhọn nói rõ body là gì: ResponseEntity<TodoResponse> có body là một todo, ResponseEntity<String> có body là chuỗi.

Bẫy: khai ResponseEntity<String> rồi đưa cả object exception vào .body(...). Sai kiểu — phải đưa a.getMessage(), tức chuỗi bên trong nó.

11. JSON & chuyển đổi

Vì sao cần JSON: object Java chỉ tồn tại trong bộ nhớ máy chủ, không gửi qua dây mạng được. JSON là cách viết object thành văn bản mà mọi ngôn ngữ đều đọc được. Jackson là thư viện làm việc dịch hai chiều đó, Spring Boot đã kèm sẵn.

Bốn luật viết JSON

  1. Tên field luôn trong nháy kép: "title", không phải title.
  2. Giá trị chuỗi trong nháy kép, còn số và true/false thì không.
  3. Không có dấu phẩy sau phần tử cuối — Java cho phép, JSON thì không.
  4. Ngoặc nhọn { } là một object, ngoặc vuông [ ] là một danh sách.

Đó là lý do GET /api/todos trả về [ ... ] còn GET /api/todos/52 trả về { ... } — một cái là danh sách, một cái là object đơn.

Jackson khớp field bằng cách nào

Không đọc field trực tiếp mà đi qua getter và setter. Chiều vào: cần setter (hoặc constructor). Chiều ra: cần getter. Thiếu getter thì field lặng lẽ biến mất khỏi JSON, không lỗi gì.

12. DTO

Sinh ra để giải quyết chuyện gì: nếu Controller nhận và trả thẳng Todo thì hình dạng bảng database bị phơi ra ngoài internet. Đổi tên cột là vỡ client. Thêm cột nhạy cảm (mật khẩu chẳng hạn) là lộ ra ngoài mà không ai để ý.

DTO = Data Transfer Object. Hai class riêng cho hai chiều:

ClassChiềuChứa gì
TodoRequestVàotitle, completed — không có id, vì id do database sinh
TodoResponseRaid, title, completed — có id vì client cần biết vừa tạo ra cái nào

TodoResponse có constructor 3 tham số để dựng nhanh trong một dòng.

Ranh giới quan trọng: Todo ở lại bên trong, không bao giờ đi ra khỏi Service. Controller chỉ thấy DTO. Đây là lý do sau khi thêm DTO thì cả 5 endpoint đều phải sửa kiểu trả về.

13. Validation

Sinh ra để giải quyết chuyện gì: client có thể gửi bất cứ thứ gì. Không kiểm thì dữ liệu rác vào thẳng database. Kiểm bằng if/else trong Service thì lặp ở mọi method. Validation cho phép khai điều kiện ngay trên field và Spring tự kiểm.
Thành phầnViệc của nó
@NotBlankĐặt trên field title của TodoRequest: không được null, không được chuỗi rỗng, không được chỉ toàn khoảng trắng
@ValidĐặt trước @RequestBody ở Controller: bật việc kiểm. Không có nó thì mọi @NotBlank nằm im

Cần dependency validation trong pom.xml, không có sẵn theo Web.

Chuyện gì xảy ra khi sai

Spring dừng trước khi gọi Controller, ném MethodArgumentNotValidException, trả 400.

Đã kiểm chứng 20/8: body 400 hiện ra là timestamp / status / error / path — bản mặc định của Spring Boot, không phải mình viết. Nó không nói field nào sai. Câu message trong @NotBlank không tới được client.

Lý do: GlobalExceptionHandler mới chỉ bắt TodoNotFoundException, không khớp handler nào nên rơi vào bộ xử lý mặc định.

Nhớ cặp đối chiếu: 404 đi qua handler mình viết, 400 không đi qua.

14. Exception & handler

Class exception riêng

public class TodoNotFoundException extends RuntimeException {
    public TodoNotFoundException(String message) {
        super(message);
    }
}
Vì sao cần class riêng thay vì ném exception có sẵn: để handler bắt đúng loại. Ném RuntimeException chung thì handler không phân biệt được "không tìm thấy" với mọi lỗi khác.
Bug đã ngốn phần lớn buổi 20/8: ban đầu class này tự khai private final String message và constructor chỉ gán this.message = message, không gọi super(message).

Hậu quả: status 404 đúng, nhưng body rỗng trắng — Postman phải chuyển sang tab Raw vì không có JSON nào để hiện.

Cơ chế: object lúc đó mang hai field cùng tên message — cái tự khai giữ chuỗi, cái của lớp cha vẫn null. getMessage() là method kế thừa, chỉ đọc field của lớp cha. Không phải ghi đè: hai field cùng tồn tại, không cái nào đụng cái nào.

Cách đúng: không khai field nào cả — Throwable đã lo việc lưu message. Chỉ cần super(message).

Dấu hiệu nhận ra lần sau: exception ném đúng, status đúng, mà body trống → nghi ngay getMessage() trả null.

Handler tập trung

@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(TodoNotFoundException.class)
    public ResponseEntity<String> handle(TodoNotFoundException a) { ... }
}
AnnotationViệc của nó
@RestControllerAdviceClass này bắt exception cho toàn bộ Controller trong app, không phải riêng một cái
@ExceptionHandler(X.class)Method này lo đúng loại exception X
Vì sao gom về một chỗ: nếu mỗi Controller tự try/catch thì cùng một loại lỗi được xử lý mỗi nơi một kiểu. Handler tập trung đảm bảo mọi endpoint trả lỗi giống nhau — và nó là chỗ duy nhất được phép biết mã HTTP nào ứng với exception nào.

17. Lỗi đã mắc — danh sách để tự canh

Khi gõ code

  • Đưa DTO cho repository.save() — 3 lần. Repository chỉ nhận Entity.
  • Thêm dòng mới mà quên xoá dòng cũ — 2 lần, khiến save hoặc findById chạy hai lần. Khi sửa: xoá trước, gõ sau.
  • Gọi getter trần không có object đứng trước — getTitle() thay vì todo.getTitle().
  • Dùng biến của method khác — mỗi method có biến riêng, không mang tên từ chỗ này sang chỗ kia.
  • So sánh boolean với true/false — if (result == true) thay vì if (result).

Khi hiểu khái niệm

  • Trả lời "vì sao" bằng cách mô tả lại đề bài thay vì nêu nguyên nhân — lỗi lặp nhiều nhất.
  • Lẫn thuật ngữ giữa các mảng, diễn đạt khái niệm này bằng ngôn từ của khái niệm khác.
  • Lẫn tên method Repository sang Service.
  • Gọi thẳng repository trong Controller.
  • Khái niệm đã học vẫn trôi sau 1–2 ngày — validation và ResponseEntity đều phải giảng lại từ đầu.

Ba khái niệm từng hiểu sai rồi mới chỉnh

  • bean — sai 3 lần trước khi chốt: bean là object, do Spring tạo và giữ.
  • shadowing — tưởng là ghi đè, thực ra hai field cùng tên cùng tồn tại.
  • public — tưởng là "mọi class trong cùng package"; đó là package-private.
